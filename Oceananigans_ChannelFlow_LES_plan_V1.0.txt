Oceananigans 多卡并行 Channel Flow（LES）适配性测试与性能测试方案（V1.0）
（仿 CESM POC 测试方案体例）

1. 目的与范围
本方案用于统一 Oceananigans.jl 在投标人/厂商所提供远程测试环境上的适配性验证与性能评测方法、取证要求及结果提交格式。测试结果将作为项目 POC 评分依据之一。

2. 通用前提、约束与取证要求

2.1 通用前提
（1）Oceananigans 版本：投标人需明确所用源码来源（官方仓库/镜像/内部分发包）及版本标识（tag/commit）。
（2）运行形态：允许“原生部署（Native）”或“容器部署（Container）”。投标人必须在报告中明确部署形态。
（3）测试环境：由投标人提供可访问的远程资源与账号权限，并在规定窗口内按本方案执行测试。
（4）多节点运行：所有测试均要求在多节点多 GPU 环境完成（不得仅在单节点模拟），并使用可复核的并行机制（推荐 MPI.jl 域分解或等价方案）。
（5）资源隔离：测试期间应尽量提供独占/隔离计算资源，避免其他作业干扰性能测量。

2.2 环境验真与取证（必须提供）
投标人需在测试前提供并协助确认以下信息，采购方将截图/留存作为证据：
·硬件清单：CPU 型号/主频/每节点核心数、内存容量；GPU 型号与显存；节点数量；GPU 拓扑（如 nvidia-smi topo -m）。
·网络：互连类型（InfiniBand/以太网）、速率、关键配置（MTU、IB 速率等）。
·软件栈：操作系统版本、内核版本；编译器版本（如涉及）；MPI 实现与版本；Slurm（如有）版本；
        Julia 版本；Oceananigans/CUDA.jl/MPI.jl 版本；I/O 依赖（NetCDF/HDF5/JLD2 等）版本。
·运行配置：网格规模、时间步长、LES 闭合、并行分解方式、进程/线程/绑定策略、I/O 频率等。

2.3 性能计时口径（必须遵循）
·仅统计“主模拟段 wall time”（从进入 time-stepping loop 开始到正常结束），不包含排队时间。
·Julia 首次启动的预编译/JIT 开销需单独记录，并与主模拟段 wall time 区分。
·同时记录吞吐指标（必须可复核）：建议至少输出 MCells/s（每秒更新网格单元数）或 SimTime/day，并在日志中打印计算口径。

2.4 结果提交物（必须提供）
每个测试项需提交以下材料（压缩打包）：
·完整工程目录（CASE_ROOT）：Project.toml、Manifest.toml、运行脚本、配置文件、作业脚本。
·运行证据：作业ID、节点清单、stdout/stderr、rank→GPU 映射、计时日志（主模拟段 wall time、吞吐）。
·输出/统计：至少 1 份可读场输出（NetCDF/JLD2）与统计输出（平均速度剖面、壁面摩擦/阻力等）。
·若采用容器：镜像信息（镜像名、版本、digest、构建方式）、运行命令与挂载策略、容器内软件栈版本。

3. 测试项一：适配性测试（Channel Flow LES，短时运行）

3.1 测试目标
验证 Oceananigans 在投标人集群上可成功运行多节点多 GPU 并行的 Channel Flow LES 案例，且输出结构与关键统计结果正常、可追溯。

3.2 测试配置（基准）
（1）算例：不可压缩湍流通道流（x/z 周期，y 固壁无滑移）。
（2）LES 闭合：WALE（或采购方指定闭合；投标人必须声明）。
（3）Re 数：建议 Re_τ=180（POC 友好）。
（4）域尺寸（示例）：Lx=2πδ，Ly=2δ，Lz=πδ。
（5）网格（示例）：Nx×Ny×Nz=256×192×256（采购方可按资源调整并固定）。
（6）并行规模（强制）：≥2 节点、总 GPU 数 ≥4。
（7）运行时长：固定步数（示例 5000 steps）或固定物理时间；以稳定跑完并产出统计为准。
（8）输出：至少 1 份场输出 + 统计输出（速度剖面、壁面摩擦/阻力、散度检查等）。

3.3 参考执行步骤（示例）
（1）依赖固定：在 CASE_ROOT 内准备 Project.toml/Manifest.toml；执行 instantiate + precompile（作为预热证据）。
（2）多节点多 GPU 运行：通过作业系统提交（如 Slurm sbatch），用 srun 启动 Julia；
     日志打印版本信息、网格/分解、GPU 列表与 rank→GPU 映射。
（3）计时：在日志中明确“主模拟段开始/结束”，输出 wall time 与吞吐指标。

3.4 通过判据（必须同时满足）
1）运行成功：作业正常结束（退出码 0），无致命错误；无 NaN/Inf/发散（若出现需解释并复现通过后方可算通过）。
2）多节点多 GPU 真实性：提交节点清单、通信/分解证据与 rank→GPU 映射，证明跨节点并行实际启用。
3）输出正常：存在可读输出文件（NetCDF/JLD2），可提供变量清单或 header 片段。
4）基本物理合理性：散度指标在阈值内；壁面摩擦相关量为正且稳定；平均速度剖面形态合理并可复核。

4. 测试项二：性能测试（3 类）

4.1 通用计时方法（必须遵循）
·性能统计仅使用主模拟段 wall time（剔除首次预编译/JIT）；同时提交预热段与主模拟段两类证据。
·每个规模至少运行 1 次；时间允许建议重复 2 次并报告波动。
·测试期间尽量独占资源；如不能独占，需记录节点负载并在报告中说明。

4.2 性能测试 A：多 GPU 线性扩展（Strong scaling）
目的：评估不同 GPU 规模下加速比与扩展趋势。
配置：与适配性测试一致（Re/网格/闭合固定）；运行时长建议更长以稳定计时；I/O 降频。
规模：以 8 GPU 为基数，建议至少测试 8/16/32/64 GPU（可上不封顶）。
Speedup(N)=T(8)/T(N)，T 为主模拟段 wall time。

表格模板：
GPU数 | 节点数 | Wall time (hh:mm:ss) | 吞吐(MCells/s 或 SimTime/day) | Speedup | 备注（MPI/绑定/分解）

32    |        |                      |                               |         |
64    |        |                      |                               |         |

4.3 性能测试 B：关键物理/闭合选项开销（固定规模）
目的：量化增强闭合/额外输运等关键选项的吞吐影响，并验证可运行性。
固定规模：例如 32 GPU（或采购方指定）。
对比项：B1（基线闭合） vs B2（增强闭合/额外被动标量等），需在招标文件固定并可复核。
输出校验：必须提交增强项对应变量存在/日志行证据（变量清单或 header 片段）。

表格模板：

4.4 性能测试 C：集合（Ensemble）吞吐测试（10 成员）
目的：评估多成员批量运行场景下的吞吐与运维组织能力。
配置：10 成员；每成员固定步数/物理时长；成员差异使用不同随机扰动 seed（必须记录）。
执行：允许串行或并行，但需如实记录并发度、总耗时与资源占用。
输出：每成员均需成功完成并产出输出；提交成员级结果表与总汇总。
