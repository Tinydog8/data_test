Oceananigans 多卡并行 Channel Flow（LES）适配性与性能测试评分说明（V1.0）
（仿 CESM POC 评分说明体例）

1. 文档目的
本文件用于规范 Oceananigans（Channel Flow LES 多 GPU 并行）在投标/POC 阶段的评分口径、取证要求与计分方法，
确保各投标人在不同硬件方案下仍可采用“同规则、可复核”的方式进行横向对比，并将测试结果可追溯地折算为评审分值。

2. 适用范围与测试方式
·适用软件：Oceananigans.jl（以采购方发布的 tag/commit 为准）。
·测试方式：厂商提供远程可用的测试环境；采购方按统一测试包与统一计分规则进行实测；厂商提供必要配合（账号、环境说明、故障排查）。
·测试期间禁止临时更换硬件规格或关键软件版本；如需变更必须重新验真并说明原因。
·网络与访问：测试环境需可通过采购方指定方式访问；禁止在测试期间临时更换硬件规格或关键软件版本。
·测试包内容（建议采购方下发并固化）：案例配置（网格/运行时长或步数/物理模型/输出频率）、运行脚本模板、参考输出（用于合理性检查）、取证清单与结果表格模板。

3. 通用前提与取证要求（所有测试项共用）
·环境等价性：测试环境须与投标承诺交付配置一致或可证明等价；建议提交《环境清单与等价性声明》（盖章/签字）。
·软件栈固定：必须提交 Project.toml/Manifest.toml 与运行脚本；允许优化但需可复现。
·运行取证：每次测试需保留作业脚本、作业ID、节点清单、wall time、stdout/stderr、关键配置摘要、吞吐日志行。
·多节点多 GPU 真实性：必须提供 rank→GPU 映射与跨节点并行证据。
·结果归档：按测试项目录结构打包，并给出文件清单与必要的哈希（md5/sha256）。
·容器说明：允许以容器方式适配/运行；但必须明确标注“原生/容器”。
·合理性检查：未通过合理性检查的测试结果视为不合理，对应软件项计 0 分（含性能与适配性）。
·一致性约束：不得通过更改网格/步数/物理模型/精度/I/O 频率等方式改变工作量而影响性能对比；若发现与测试包不一致，视为不通过。

4. 评分总则
评分采用“通过性约束 + 归一化相对评价”的组合方式：先进行适配性与合理性检查，仅对通过检查者进入计分；
再基于入围厂商实测区间进行归一化评分。

4.1 归一化评分通用公式
（1）小者优（如 wall time、GPU-hour）：
    S = S_max × (C_max − C_i) / (C_max − C_min)
（2）大者优（如吞吐、并行效率）：
    S = S_max × (C_i − C_min) / (C_max − C_min)
若 C_max = C_min，则所有通过检查者该项得分均为 S_max；未通过检查者该项得分为 0。

4.2 GPU 归一化口径（可选，跨代际 GPU 建议启用）
如需跨不同 GPU 架构公平对比，可引入单位 GPU 性能基准 P_i（以采购方指定基准为准，如 GPU-HPL 或 Oceananigans 微基准）。
设 P_ref 为入围厂商中最大值，F = P_ref / P_i。
·归一化 GPU 数：G_norm = G_raw × F
·归一化 GPU-hour：Σ(G_norm × walltime_hour)
启用则必须提交基准测试原始日志。

4.3 一票否决（不通过则 Oceananigans 项总分为 0）
满足任一情形可判定不通过：
（1）未在多节点多 GPU 上完成（例如仅单节点/单 GPU 或无法证明跨节点并行）。
（2）未提供完整可复核证据（Project/Manifest/作业脚本/日志字段/输出文件缺失）。
（3）运行异常退出、出现 NaN/Inf 或明显数值发散且无法解释并复现修复。
（4）关键配置与测试包不一致（网格、步数/物理时长、闭合模型、精度口径、固定规模点等）。
（5）合理性检查不通过或结果明显不合理（见 5.2）。

5. Oceananigans 适配性测试及评分（满分：0.8）

5.1 测试内容与通过判据
适配性测试目标：验证 Oceananigans 在投标人所提供的多节点多 GPU 环境中可正确运行指定 Channel Flow（Nonhydrostatic + T/S + drag）案例，并产出可复核输出。

测试案例（以采购方发布测试包为准；建议与脚本保持一致）：
·模型：NonhydrostaticModel + tracers(:T,:S) + SeawaterBuoyancy + AnisotropicMinimumDissipation
·底部：drag 通量边界（需可复核 z0、κ、z1 与 cᴰᵇ）
·对流/时间推进：WENO(order=9) + RungeKutta3 + TimeStepWizard(cfl=0.8,max_change=1.1,max_Δt=0.1minute)
·运行终止：采购方在测试包中固定一种口径（建议二选一并固化，不得投标人自改）：
  - stop_time=4hours（与你脚本一致），或
  - stop_iteration=1000（便于窗口固定与对齐）
·网格/输出频率：由测试包固定（可用你的 Nx=100,Ny=100,Nz=50 作为基准；也可上调但必须所有投标人一致）

通过判据（全部满足）：
1）成功完成作业运行并正常退出（退出码 0），无 NaN/Inf/发散导致的异常终止；
2）多节点多 GPU 并行证据完整（节点列表 + MPI ranks + rank→GPU 映射，且证明跨节点运行）；
3）输出目录结构完整且可追溯：包含 stdout/stderr、run_config、timing/统计文件、以及至少 1 份输出数据文件；
4）输出文件可正常读取：关键变量至少包含 u、v、w、T、S（格式允许 JLD2/NetCDF，由测试包规定其一或两者）；
5）通过合理性检查（见 5.2）。

5.2 合理性检查（不通过则 Oceananigans 全部测试为 0）
采购方提供参考输出（reference output），并对投标人输出进行一致性核验。建议至少包含以下 3 类指标（窗口必须在测试包中固定）：

（1）平均流速剖面 u_bar(z)
·统计窗口：若 stop_iteration=1000，建议取第 800–1000 step；若 stop_time=4hours，建议取末段（例如最后 20% 迭代或最后 1 小时）的时间平均。
·核验：与参考剖面做相关系数 corr(u_bar_vendor, u_bar_ref)
·阈值建议：corr ≥ 0.98

（2）温度/盐度均值剖面 T_bar(z), S_bar(z)
·同一统计窗口
·核验：corr(T_bar_vendor, T_bar_ref) 与 corr(S_bar_vendor, S_bar_ref)
·阈值建议：corr ≥ 0.97

（3）全局动能时间序列 KE(t)（或等价能量/速度模统计）
·核验：corr(KE_vendor, KE_ref)
·阈值建议：corr ≥ 0.95

补充的硬性检查（任一失败即判不通过）：
·u,v,w,T,S 任一字段出现 NaN/Inf；
·不可压缩约束明显失效（如 divergence 指标远超阈值且无法解释）；
·底部 drag 参数/形式与测试包不一致；
·通过改变网格/步数/输出频率等改变工作量。

说明：
·相关系数建议使用 Pearson 相关（对同一 z 网格或插值到同一 z 采样点后计算）；具体实现可由采购方提供脚本统一核验。
·未达阈值判为不合理：Oceananigans 全部测试记 0 分，不再进入性能计分。

建议进一步核验（可选但强烈建议纳入测试包）：
·全局动能/耗散趋势：在统计窗口内不应出现非物理爆炸式增长。
·壁面剪切应力分布：符号与量级合理，且与平均速度剖面一致。
·（若提供参考输出）空间相关系数/关键统计量误差：给出阈值并按同一窗口对比。

5.3 计分规则
适配方式                                  得分
原生适配（不依赖容器，或仅用系统原生模块/环境）  0.8
容器适配（以容器方式完成运行）                  0.5
不适配/无法完成/未通过合理性检查                0

5.4 适配性扣分项（可选）
如采购方希望更细粒度区分“通过但证据不全”的情况，可设置扣分项（总分不低于 0）：
·缺少关键日志字段（版本/网格/绑定/计时分段等）扣 0.05~0.10
·缺少输出文件清单或无法复核变量/格式扣 0.05~0.10
·未提供作业脚本原件仅提供截图扣 0.05
（是否启用以采购文件为准；未启用则仍按 5.3 三档计分）

6. 性能测试及评分（满分：2.0）
性能总分：S_perf = S_A + S_B + S_C（满分 2.0）。
容器扣分（示例）：若某子测试在容器中完成，则该子测试得分乘以 0.7。

6.1 子测试A：多 GPU 扩展性能（满分：1.0）
·案例：Channel Flow LES（与测试方案一致）。
·要求：至少完成基数规模 + 3 个扩展点（如 8/16/32/64 GPU）。
·并行效率（并截断到 [0,1]）：
    E_N = (T_base / T_N) / (N / N_base)
·平均并行效率：
    E_i = mean(E_16, E_32, E_64)  （缺项则按已测点平均，但至少需提供 N_base + 1 个扩展点）
·时间指标：T_i = T_base（例如 T_8，单位秒；仅取主模拟段 wall time）。
·计分（示例权重）：
  - 时间得分 0.6：对 T_i 做“小者优”归一化；
  - 效率得分 0.4：对 E_i 做“大者优”归一化；
  - 子测试A得分：S_A = 1.0 × (S_time + S_eff)。

补充说明：
·T_base 仅取“主模拟段 wall time”（剔除 JIT/预热）；若未分段提供，视为证据不全，可判 0 分或扣分（以采购文件为准）。
·若扩展点缺项：至少需提供“基数 + 1 个扩展点”，否则子测试A计 0；其余按已测点平均 E_i。

6.2 子测试B：关键选项吞吐（满分：0.5）
·固定规模（如 32 GPU 或采购方指定）。
·指标：增强配置（B2）的吞吐（大者优，MCells/s 或 SimTime/day）。
·证据要求：必须提交开关校验证据（变量存在/日志行）；未提供则该子测试计 0 分。
·计分：对吞吐做“大者优”归一化得到 S_B。

建议计分细化（可选）：
·若同时提交 B1 与 B2，可额外计算“开销比”R = throughput_B2 / throughput_B1，用于合理性检查（R 不应 >1.2 等异常值；阈值以模型定义为准）。

6.3 子测试C：集合吞吐（满分：0.5）
·任务：10 成员集合运行（每成员固定步数/物理时长）。
·建议指标：总归一化 GPU-hour 成本（小者优），或按采购方指定的等价成本口径。
·完成度约束：未完成 10 成员者先按完成比例 k/10 折算，再计分；缺少有效证据材料则该子测试计 0 分。
·计分：对集合成本做“小者优”归一化得到 S_C。

集合成本口径建议（便于复核）：
·若不启用 GPU 归一化：C_i = Σ (GPU_raw_j × walltime_hour_j)
·若启用 GPU 归一化：C_i = Σ (GPU_norm_j × walltime_hour_j)
其中 j 为集合成员作业；每个成员必须提供 MAIN_WALL_SECONDS 与 GPU 数证据。

7. 交付材料清单（厂商需随测试结果提交）
·环境清单与等价性声明（CPU/GPU/网络/存储/软件栈版本；如启用归一化则含基准测试 P_i 原始日志）。
·适配性测试：Project/Manifest、运行脚本、作业脚本与日志、输出目录与文件清单、合理性检查产物（曲线/统计文件）。
·性能测试A：各 GPU 规模 wall time 与吞吐、作业脚本、日志与文件清单。
·性能测试B：固定规模 wall time、吞吐、开关校验证据与输出。
·性能测试C：10 成员作业记录（每成员 GPU 数、wall time、吞吐）、总成本计算表、输出与文件清单。
·如使用容器：镜像 digest/tag、构建与运行命令、容器内软件栈版本与可复现说明。

附：建议采购方最终汇总表字段（便于招标评分落表）
·适配性：原生/容器；是否通过合理性；证据完整性（是/否）
·性能A：T_base、各点 speedup、E_i
·性能B：吞吐（MCells/s 或 SimTime/day，B2）与证据行
·性能C：总 GPU-hour（或归一化 GPU-hour）、完成比例

6.4 Oceananigans 性能总分与总分口径（建议）
·性能总分：S_perf = S_A + S_B + S_C（满分 2.0）
·Oceananigans 总分：S_total = S_compat + S_perf（满分 2.8，其中 S_compat 满分 0.8）
